# 基准采集套件

对应论文的实验章节。三块内容：`size.mjs`（产物体积，表 2）、`index.html`（浏览器采集页，表 1、3~7）、
`assets/`（程序化生成、可复现的六面贴图）。

---

## 一、怎么跑

```bash
npm run build          # 先产出 dist/
npm run bench          # = 生成贴图 + 体积统计 + 起服务（5174）
```

浏览器打开 <http://localhost:5174/bench/>。想换贴图尺寸：

```bash
node scripts/gen-assets.mjs --size=2048   # 生成 bench/assets/2048/ 六张 PNG
# 然后打开 http://localhost:5174/bench/?size=2048
```

`bench/assets/` 与 `bench/out/` 已在 `.gitignore` 里：贴图是脚本现场画的，不占仓库体积。

## 三、实测踩到的坑（写论文时要知道）

这四条都是在本机真跑时撞出来的，不是理论推演。

**1. `restoreContext()` 不能在丢失事件的同一任务里调用。**
Chrome / ANGLE 上，`webglcontextlost` 回调里立刻 `restoreContext()`，有相当概率永远不派发
`webglcontextrestored`，页面静默卡死。采集页的处理是：等 120 ms 再请求恢复，并对恢复事件
设 2.5 s 超时、最多重试 3 次，失败计入「失败次数」列而不是挂起。

**2. `gl.finish()` 在 ANGLE / D3D11 上不阻塞。**
实测 `finish()` 前后读数恒为 0.1 ms，与 `readPixels` 能读到正确像素的事实矛盾。所以单帧耗时
改用 `readPixels(0, 0, 1, 1)` 强制同步，这一行才包含 GPU 光栅化等待。

**3. `performance.now()` 分辨率不够测单帧。**
非跨源隔离页面上被钳到 100 µs，而单帧提交只要几十微秒，逐帧计时会读到大量 0。因此改为
批量计时再除以帧数（提交：30 批 × 30 帧；同步：20 批 × 5 帧），并在计时前预热 12 帧。

**4. 纹理对象不能跨 WebGL 上下文共享。**
这是 WebGL 的硬约束，不是实现缺陷。因此表 5 的多实例实验必须让所有实例落在同一个
canvas 上——`canvas.getContext('webgl')` 重复调用返回同一上下文，资源池才有共享的前提。
**论文里的表述要收窄**，建议写成：

> 资源池以图形上下文为隔离单位。同一页面内复用同一 canvas 的实例（典型场景是路由切换、
> 同一视口内重复创建）共享同一份立方体贴图；跨 canvas 的场景受 WebGL 规范限制无法共享，
> 此时每个上下文仍需各自持有一份纹理。

不要写成「同页多实例显存恒为常数」，跨 canvas 时不成立，审稿人一眼能看出来。

**5. 显存是估算值。**
浏览器不提供读取 GPU 显存的接口。表中数字按 `6 × 边长² × 4 字节 × 份数` 折算，表头需注明
「估算」。`performance.memory` 只反映 JS 堆，不能代表显存。

**6. 本地服务对贴图发了 `Cache-Control: no-store`。**
所以每次试验都是真实下载，属于偏保守的测法；生产环境命中 HTTP 缓存时数字会更低。这一点在
表 3、表 6 的脚注里要写清楚，否则读者会以为你在最好的条件下取数。

## 四、采样量建议

| 实验 | 建议 | 理由 |
|---|---|---|
| 冷启动 | N = 30 | 首帧受 JIT 与管线预热影响大，少于 30 次分位数不稳 |
| 稳态帧间隔 | 3000 帧（约 50 s） | 要覆盖至少一次 GC 与后台任务抖动 |
| 多实例显存 | 1 / 2 / 4 / 8 | 够看出线性与常数的差别，再往上受设备纹理上限限制 |
| 丢失恢复 | N = 20 | 单次波动大，20 次的中位数才有说服力 |

采集页面的输入框都允许改小，调试时用 3 / 300 / 2 先跑通，正式取数再改回上表。
